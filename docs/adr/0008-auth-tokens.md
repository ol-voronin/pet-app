# 0008 — Авторизация: OTP по телефону, короткий access JWT, ротируемый refresh

- Статус: Принято
- Дата: 2026-11-19

## Контекст
Вход по номеру телефона (Viber → SMS), позже Apple/Google. Мобильный клиент работает офлайн и
живёт долго; токены лежат в SecureStore. Нужна защита от перебора кода и от кражи refresh-токена.

## Варианты
1. **Свой модуль: OTP + JWT (jose) + refresh-сессии в Postgres** — полный контроль, никаких внешних
   зависимостей и платы за пользователя; сами отвечаем за безопасность (покрыто тестами).
2. **Готовый провайдер (Neon Auth / Supabase Auth / Firebase Auth)** — меньше кода, но телефонный OTP
   через Viber и украинские SMS-шлюзы там не из коробки, данные пользователей у третьей стороны, цена растёт с MAU.
3. **Сессии без JWT (opaque-токен, проверка в БД на каждый запрос)** — проще отзыв, но запрос в БД на каждый
   вызов API. Сейчас мы всё равно проверяем сессию в `authenticate`, так что разница невелика; JWT оставляет
   возможность убрать эту проверку для «дешёвых» эндпоинтов.

## Решение
Вариант 1.
- OTP: 6 цифр, 5 минут, 5 попыток; не чаще 1 кода в 60 с и 3 кодов за 10 мин на номер. В БД — только HMAC кода,
  привязанный к телефону. В dev — `OTP_FIXED_CODE` (запрещён в production), доставка — в лог.
- Access: JWT HS256, 15 минут, `sub` = user, `sid` = session; при каждом запросе проверяется, что сессия жива
  (logout и отзыв действуют сразу).
- Refresh: случайные 32 байта, 60 дней, в БД — HMAC. Ротация на каждый `/auth/refresh`; повтор старого токена
  отзывает всю «семью» сессий этого входа.
- Телефон нормализуется в E.164 только для украинских номеров (`+380…`).

## Последствия
- Секрет `JWT_SECRET` (≥ 32 символов) — в переменных окружения сервера.
- Production-доставка кода (Viber → SMS) — отдельная задача; без неё сервер в production не стартует.
- Apple/Google добавятся как новые `auth_identities.provider` без изменения схемы сессий.
