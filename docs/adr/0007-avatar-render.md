# 0007 — Рендер 3D-аватара питомца

- Статус: Предложено (ждёт решения владельца)
- Дата: 2026-11-20
- Связанные документы: `docs/PRD.md`, `HANDOFF.md` (§6), `packages/db/src/schema/pets.ts`, `tools/avatar/balloon_pets.py`, `docs/design/avatar-sample.png`, ADR-0006, ADR-0009.
- Данные о пакетах и размерах проверены 20.11.2026 по npm registry, PyPI/Blender и замерам репозитория (ссылки внизу).

## Контекст

По `docs/PRD.md` у каждого питомца по умолчанию есть нарисованный 3D-аватар в стиле глянцевых «фигурок из шариков» (`docs/design/avatar-sample.png`), который собирается автоматически по виду и породе и правится владельцем в конструкторе. В MVP:
- виды: только `dog` и `cat`;
- 4 параметра в конструкторе: `ears` (уши), `muzzle` (морда), `coat` (шерсть), `color` (окрас);
- в БД уже заложены `pets.avatar` (`jsonb`: `species`, `ears`, `muzzle`, `coat`, `color`, `renderVersion`) и `pets.avatar_key` (ключ объекта в приватном бакете);
- на экране «Дім» в ряду одновременно отображаются аватары всех питомцев семьи (сценарий проверки — 3 питомца);
- без сети медкарта работает в режиме чтения из кэша (ADR-0003 отложен после MVP);
- сквозное требование — стабильная работа на слабых Android (2–3 ГБ ОЗУ);
- ограничение владельца — **0 доплаты** (используем уже оплаченный выделенный сервер Hetzner из ADR-0009 и Neon Object Storage 5 ГБ бесплатно из ADR-0006);
- мобильный стек: Expo SDK `58.0.26`, React Native `0.88.1` (New Architecture / Fabric), React `19.3.0`.

Уже существует рабочий прототип `tools/avatar/balloon_pets.py` (`bpy 5.3.0`, Python 3.13, Cycles CPU, 48 семплов + denoising): рендер 8 фигурок `420×500` на 2 ядрах CPU занял **≈ 2,5 минуты** (~18–20 с на одну картинку). Итоговая сетка `docs/design/avatar-sample.png` (`1680×1000`, 8 фигурок) весит **613 КБ** (в среднем **~76 КБ** на аватар в PNG; при сжатии в WebP — ещё меньше).

### А. 3D в приложении (`expo-gl` + `three` + `@react-three/fiber`)
Сцена строится из примитивов (или загружается `.glb`) прямо на телефоне через OpenGL ES (`expo-gl`). Использование `expo-three` не рассматривается как основное: пакет не помечен deprecated, но фактически стал legacy-прослойкой, а экосистема перешла на `@react-three/fiber`.
- **Плюсы:** нулевая нагрузка на сервер; мгновенное изменение любого параметра и произвольного цвета; конструктор работает офлайн; можно вращать фигурку.
- **Минусы:**
  - На экране «Дім» с 3+ питомцами нельзя держать несколько активных `GLView` на слабом Android — всё равно придётся рендерить в offscreen-текстуру / PNG и кэшировать, то есть писать двойную логику.
  - Сложно добиться мягкого студийного света, clearcoat-бликов и теней уровня Cycles (`docs/design/avatar-sample.png`) на мобильном OpenGL ES без тяжёлых HDRI/PMREM, что бьёт по памяти и времени старта.
  - Дополнительный риск при обновлениях Expo SDK / React Native New Architecture (Fabric flattening, R8 shrinking правил для `expo.modules.gl.**`, утечки нативных буферов при unmount).
  - Увеличивает размер бандла и время сборки EAS.

### Б. Готовая картинка с сервера по запросу (`bpy` / Blender Cycles)
Воркер на выделенном сервере Hetzner (рядом с API и BullMQ из ADR-0009) получает задачу с параметрами `pets.avatar`, рендерит PNG/WebP через `balloon_pets.py` (Blender Cycles CPU), сохраняет в Neon Object Storage (`pets/<petId>/avatar/<hash>.png` или общий кэш по хешу параметров) и обновляет `pets.avatar_key`.
- **Плюсы:** 100% визуальное качество `avatar-sample.png`; 0 КБ новых зависимостей в мобильном приложении; минимальная нагрузка на слабые Android; переиспользуется готовый `balloon_pets.py`; поддерживает неограниченное число параметров и произвольные цвета в будущем.
- **Минусы:**
  - Пакет `bpy` для Linux (`manylinux_2_28_x86_64`) весит ~350–370 МБ при скачивании и **> 1 ГБ** в распакованном виде, жёстко привязан к версии Python и раздувает Docker-образ.
  - Один рендер на 2 ядрах CPU занимает ~18–20 с (по замеру `HANDOFF.md` §6): для живого перебора вариантов в конструкторе это слишком медленно — пользователю придётся ждать или смотреть заглушку до нажатия «Зберегти».
  - Нужен отдельный сервис/воркер в `deploy/docker-compose.yml` и защита от перегрузки CPU (очередь, лимит параллельных рендеров).

### В. Заранее отрендеренные картинки
Имеет два принципиально разных подхода:
1. **В1 — Послойная сборка частей в приложении** (отдельно тело, голова, уши, морда, хвост, окрашиваемые в приложении):
   - Для плоских 2D-иллюстраций работает хорошо, но для глянцевых 3D-шариков в ракурсе три четверти (`HANDOFF.md` §6) **не подходит**: отражения окружения, блики на стыках сфер и тень на полу (`shadow_catcher`) зависят от взаимного расположения деталей, а перекрашивание через `tintColor` портит блики на белом и чёрном окрасах.
2. **В2 — Предрендер матрицы комбинаций MVP оффлайн-скриптом и раздача из S3**:
   - В MVP всего 4 дискретных параметра (`ears`, `muzzle`, `coat`, `color`) и 2 вида (`dog`, `cat`). Например: `2 вида × 4 формы ушей × 3 морды × 3 шерсти × 8 окрасов = 576` готовых картинок.
   - Они рендерятся один раз скриптом `balloon_pets.py` при обновлении `renderVersion` (576 штук ≈ 3 часа на 2 ядрах или ~30–45 мин на 8+ ядрах), конвертируются в WebP/PNG и загружаются в хранилище по детерминированному ключу `avatars/v{renderVersion}/{species}-{ears}-{muzzle}-{coat}-{color}.webp`.
   - Объём в S3: `576 × ~70 КБ ≈ 40 МБ` (менее 1% от бесплатных 5 ГБ Neon Object Storage).
   - **Плюсы:** 100% качество Cycles и ракурс 3/4; **0 КБ** в сборке приложения; **0 нагрузки** и **0 лишних контейнеров** на сервере Hetzner; мгновенное переключение вариантов в конструкторе (< 200 мс на загрузку файла); нулевой риск по Expo SDK 58 и слабым Android.
   - **Минусы:** фиксированный набор значений (нет произвольного color picker); при росте комбинаций (например, > 3 000 в V2 с аксессуарами/пятнами) матрица станет слишком большой — тогда потребуется переход на Вариант Б.

## Решение (рекомендация команды)

**Рекомендуем Вариант В2 на MVP с бесшовным путём к Варианту Б в V2** (единый контракт `pets.avatar` + `pets.avatar_key`):

1. На этапе MVP (Этап 5b) доводим 3D-модели в `tools/avatar/balloon_pets.py` (ракурс три четверти, контраст белого окраса, размер глаз) и фиксируем дискретные значения 4 параметров (ориентир — до ~600 комбинаций).
2. Рендерим матрицу один раз локально / в CI-артефакт и кладём готовые файлы в бакет (ADR-0006) по детерминированному ключу с префиксом `renderVersion`.
3. Мобильное приложение показывает аватар обычным `<Image>` и кэширует картинку на устройстве для офлайн-режима; конструктор при переключении чипов сразу показывает соответствующий предрендер.
4. Когда в V2 появятся произвольные окрасы, пятна или аксессуары (комбинаторный взрыв), подключаем серверный воркер `bpy` на Hetzner (Вариант Б) как генератор по промаху кэша (cache-miss) в том же бакете — **без изменений в мобильном приложении и схеме БД**.

## Последствия

- Мобильное приложение остаётся лёгким, без `expo-gl` и `three`, стабильно работает на Android с 2–3 ГБ ОЗУ и в Expo Go.
- На сервере Hetzner в MVP не нужен контейнер с Blender (>1 ГБ) и не тратится CPU на рендер.
- Поле `pets.avatar.renderVersion` позволяет безопасно обновить 3D-формы в будущем, не ломая старые ссылки.
- Офлайн-редактирование конструктора в MVP недоступно — это полностью соответствует уже принятому правилу «без сети медкарта только для чтения» (`docs/PRD.md`, решение от 20.11.2026).
- Открытый вопрос из `HANDOFF.md` («кто доводит 3D-формы аватара в `balloon_pets.py`») остаётся за владельцем перед стартом Этапа 5b.
