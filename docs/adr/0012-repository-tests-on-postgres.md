# 0012 — Тесты репозиториев на настоящем Postgres

- Статус: Принято (21.11.2026, решение команды по [#62](https://github.com/ol-voronin/pet-app/issues/62); боевой код не меняется)
- Дата: 2026-11-21

## Контекст
Автотесты API работают на хранилище в памяти, поэтому SQL в `Drizzle*Repo` до сих пор проверялся руками на Neon `dev`.
Так пропустили `ORDER BY null` в поиске (PR #53) и гонку лимита семьи: два человека одновременно принимали
приглашения и оба попадали к питомцу (#50). Нужны тесты, которые выполняют настоящие запросы в CI.

Сложность: `packages/db` подключается драйвером `neon-http`. Он не открывает соединение с Postgres, а отправляет
каждый запрос по HTTPS в прокси Neon, и транзакций у него нет — только пакет `db.batch`. С обычным Postgres в
контейнере этот драйвер напрямую не работает.

## Варианты
1. **Отдельный драйвер `node-postgres` только для тестов.** Просто подключить, но у него нет `db.batch`: пришлось бы
   писать замену, и тесты проверяли бы её, а не то, что работает в бою. Разбор типов (даты, числа, jsonb) у двух
   драйверов тоже разный — ошибки такого рода тест бы не увидел.
2. **Локальный прокси Neon в контейнере** (образ сообщества `local-neon-http-proxy`). Ближе всего к бою: тот же
   прокси, что у Neon. Минусы: чужой образ без версий в CI, отдельные сертификаты и адрес `db.localtest.me`,
   два контейнера вместо одного. Цена — 0, риск — сборка CI зависит от стороннего образа.
3. **Боевой драйвер, подменён только транспорт — выбрано.** У клиента Neon есть штатная настройка
   `neonConfig.fetchFunction`. В тестах вместо HTTP-запроса в Neon тот же запрос выполняется через `pg` в локальном
   Postgres. Цена — 0; новая зависимость одна (`pg`, только для тестов).

## Решение
- Пакет `packages/db-testing` (только для тестов): `installNeonOverPg()` подменяет транспорт. Одиночный запрос
  выполняется сам по себе; пакет — `BEGIN … COMMIT` на одном соединении и откатывается целиком при ошибке, как в
  прокси Neon. Значения возвращаются текстом с типами колонок, ошибки Postgres — с кодом (`23505` и другие), поэтому
  разбор типов и обработка ошибок идут боевым кодом драйвера.
- Тесты вызывают боевую фабрику `createDb()` и боевые `Drizzle*Repo`; в них самих про подмену ничего нет.
- База: PostgreSQL 17 + PostGIS 3.5 (`postgis/postgis:17-3.5`, как в Neon). Перед прогоном создаётся отдельная база,
  в неё мигратором drizzle применяются все файлы из `packages/db/migrations`, после прогона она удаляется.
- Адрес базы — `TEST_DATABASE_URL`, принимается только `localhost`: тесты нельзя направить на Neon, staging или прод.
- Файлы тестов — `*.db.test.ts`, запуск — `pnpm test:db`. Обычный `pnpm test` их не запускает и базы не требует.
  В CI — отдельная job «repositories on Postgres» с базой как сервисом.
- `pg` не должен попасть в боевой образ API. pnpm сам подставляет его в `drizzle-orm` как необязательную зависимость,
  как только `pg` появляется где-либо в репозитории, и тогда он уезжает в образ (проверено `pnpm deploy --prod`).
  Поэтому в `pnpm-workspace.yaml` стоит `overrides` — `drizzle-orm>pg: '-'`; после этого в боевых зависимостях API
  `pg` нет (проверено тем же способом).

## Последствия
- Каждый `Drizzle*Repo` проверен хотя бы по основному сценарию: вход, питомцы, семья, карта (PostGIS и поиск
  `pg_trgm`), импорт OSM, медкарта. Гонки проверяются одновременными запросами: лимит семьи, две правки одной записи,
  два использования одного кода. Тест лимита семьи падает, если убрать блокировку из `acceptInvite` (проверено).
- Миграции проверяются на чистой базе при каждом PR.
- Новый запрос в `drizzle-repo.ts` — тест рядом в том же PR (`docs/LESSONS.md`).
- Чего тест не видит: поведение самого прокси Neon — лимит размера ответа, таймауты, пул соединений. Транспорт —
  наша имитация по коду клиента `@neondatabase/serverless` 1.2.1; при обновлении клиента её нужно сверить. То, что
  зависит от этих вещей, по-прежнему проверяется на Neon `dev` (`pnpm -F api check:family-limit` остаётся).
- Если имитация начнёт расходиться с боем, переходим на вариант 2: меняется только `packages/db-testing`.

## Источники
- Клиент Neon, настройка `fetchFunction`: `node_modules/@neondatabase/serverless/CONFIG.md`.
- Формат запроса и ответа SQL-over-HTTP — код `neon()` в `@neondatabase/serverless` 1.2.1.
